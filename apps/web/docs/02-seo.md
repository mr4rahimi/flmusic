# استراتژی و پیاده‌سازی SEO

این سند می‌گوید **چه چیزی پیاده شده**، **چرا**، و **بعد از دیپلوی چه کارهایی لازم است**.

---

## ۱. اصل کلی

گوگل چیزی را ایندکس می‌کند که در HTML اولیه‌ی پاسخ سرور باشد.
اپ‌های تک‌صفحه‌ای (SPA) محتوا را با جاوااسکریپت می‌سازند و گوگل
آن‌ها را دیرتر و ناقص‌تر می‌بیند. به همین دلیل **همه‌ی محتوای معنادار
سمت سرور رندر می‌شود** و جاوااسکریپت فقط برای پخش صوت لازم است.

اگر جاوااسکریپت را در مرورگر خاموش کنید، متن، لینک‌ها و متادیتای همه‌ی
صفحات همچنان سالم‌اند. تنها چیزی که کار نمی‌کند دکمه‌ی پخش است.

---

## ۲. ساختار URL

```
/                                      صفحه‌ی اصلی
/trending                              داغ‌ترین‌ها
/new                                   جدیدترین‌ها
/genre                                 فهرست سبک‌ها
/genre/پاپ                             آهنگ‌های سبک پاپ
/artist/mr4rahimi                      پروفایل هنرمند
/track/نام-آهنگ--<uuid>                صفحه‌ی آهنگ
/playlist/نام-پلی‌لیست--<uuid>          پلی‌لیست
/search?q=...                          جستجو (noindex)
```

### چرا `slug--uuid`؟

دیتابیس ستون slug ندارد و افزودنش یعنی migration. راه‌حل بدون تغییر
دیتابیس: عنوان را به slug تبدیل و با `--` به UUID می‌چسبانیم.
`--` انتخاب شد چون داخل slugها هم `-` وجود دارد و باید قابل‌تفکیک بماند.

- `extractId()` در [`src/lib/seo.ts`](../src/lib/seo.ts) UUID را با regex بیرون می‌کشد.
- اگر URL دقیقاً شکل canonical نباشد (مثلاً فقط UUID خام، یا عنوانی
  که بعداً عوض شده) صفحه **۳۰۸ دائمی** به شکل درست می‌دهد.
  این جلوی محتوای تکراری را می‌گیرد.

حروف فارسی در URL نگه داشته می‌شوند؛ گوگل URL یونیکد را درست ایندکس می‌کند
و برای کاربر فارسی خواناتر است.

### تک‌URL بودن

- `trailingSlash: false` — هر صفحه فقط یک آدرس معتبر دارد.
- تگ `<link rel="canonical">` روی همه‌ی صفحات ست است.
- `www.flmusic.ir` در nginx با ۳۰۱ به `flmusic.ir` می‌رود.

## ۳. متادیتا

از Metadata API خود Next استفاده شده (`src/app/**/page.tsx`).

### چه چیزی روی هر صفحه ست می‌شود

| تگ | منبع |
|---|---|
| `<title>` | عنوان آهنگ/هنرمند + نام سایت (از طریق `template` در layout) |
| `<meta name="description">` | توضیح آهنگ، یا اگر نبود متن تولیدشده از عنوان + هنرمند + سبک |
| `<link rel="canonical">` | مسیر canonical صفحه |
| `og:*` | عنوان، توضیح، تصویر ۱۲۰۰×۶۳۰، `og:type` مناسب |
| `twitter:*` | کارت `summary_large_image` |
| `<html lang="fa" dir="rtl">` | در layout ریشه |

`og:type` برای آهنگ `music.song` و برای پروفایل `profile` است — این‌ها
تلگرام و شبکه‌های اجتماعی را وادار می‌کند پیش‌نمایش غنی نشان دهند.

### توضیحات متا

`metaDescription()` متن را در **مرز کلمه** و حدود ۱۶۰ کاراکتر می‌برد.
بریدن وسط کلمه در نتایج جستجو بد دیده می‌شود.

### تصویر پیش‌نمایش

`opengraph-image.tsx` کنار هر صفحه، یک PNG ۱۲۰۰×۶۳۰ می‌سازد:
کاور/آواتار در یک طرف، عنوان و نام هنرمند در طرف دیگر، با پس‌زمینه‌ی برند.
حتی آهنگ‌های بدون کاور هم تصویر آبرومند می‌گیرند — لینک بدون تصویر
در تلگرام و توییتر کلیک به‌مراتب کمتری می‌گیرد.

#### فارسی در تصویر OpenGraph

موتور رندر `ImageResponse` (satori) دو محدودیت دارد که هر دو در
[`src/lib/og.tsx`](../src/lib/og.tsx) دور زده شده‌اند:

۱. **فونت پیش‌فرض شکل‌دهی خط فارسی را ندارد** و روی متن فارسی با خطای
   `substFormat: 3 is not yet supported` می‌شکست — یعنی تصویر OG هر
   هنرمند یا آهنگ با عنوان فارسی، خطای ۵۰۰ می‌داد. حل: فایل‌های
   Vazirmatn از `assets/fonts/` خوانده و صریح به `ImageResponse` داده می‌شوند.
   (این فایل‌ها با `outputFileTracingIncludes` به خروجی standalone اضافه می‌شوند،
   چون ردیاب وابستگی‌ها خواندن با `fs` را نمی‌بیند.)

۲. **الگوریتم bidi کامل نیست** و ترتیب کلمات فارسی را معکوس می‌کند
   («فول موزیک» → «موزیک فول»). چون معکوس‌سازی منظم است (روی فاصله و
   نیم‌فاصله)، تابع `fixRtlOrder()` از قبل جبرانش می‌کند. بخش‌های جدا از هم
   (مثل «۱۰ آهنگ · ۹ دنبال‌کننده») هرکدام در یک span مستقل داخل یک
   flex با `row-reverse` رندر می‌شوند تا ترتیبشان را flexbox تعیین کند نه bidi.

## ۴. داده‌ی ساختاریافته (Schema.org)

هر صفحه یک بلوک JSON-LD دارد که در `@graph` بسته‌بندی شده.
سازنده‌ها در [`src/lib/jsonld.ts`](../src/lib/jsonld.ts).

| صفحه | نوع‌ها |
|---|---|
| همه (layout ریشه) | `Organization`, `WebSite` + `SearchAction` |
| آهنگ | `MusicRecording` (+ `AudioObject`, `byArtist`), `BreadcrumbList` |
| هنرمند | `MusicGroup`, `ProfilePage`, `BreadcrumbList` |
| پلی‌لیست | `MusicPlaylist`, `BreadcrumbList` |
| فهرست‌ها و ژانر | `CollectionPage` + `ItemList`, `BreadcrumbList` |

### چرا این‌ها؟

- **`WebSite` + `SearchAction`** شرط لازم برای نمایش کادر جستجوی سایت
  زیر نتیجه‌ی گوگل است.
- **`MusicRecording`** به گوگل می‌گوید این صفحه یک آهنگ است، نه یک مقاله؛
  `duration`، `datePublished` و `interactionStatistic` (تعداد پخش/لایک/نظر)
  سیگنال‌های کیفیت‌اند.
- **`BreadcrumbList`** باعث می‌شود در نتایج گوگل به‌جای URL خام،
  مسیر `فول موزیک › هنرمند › آهنگ` نمایش داده شود.

### اعتبارسنجی

بعد از دیپلوی این دو را اجرا کنید:

- <https://search.google.com/test/rich-results>
- <https://validator.schema.org/>

## ۵. robots و sitemap

### robots.txt

`/search` بسته است. صفحات نتیجه‌ی جستجو بی‌نهایت URL تکراری می‌سازند
و بودجه‌ی خزش را می‌بلعند. `follow` باقی می‌ماند تا لینک‌های داخلی دنبال شوند.

### sitemap.xml

[`src/app/sitemap.ts`](../src/app/sitemap.ts) شامل صفحات ثابت، همه‌ی سبک‌ها،
همه‌ی هنرمندان و آهنگ‌ها است. `lastModified` هر آهنگ از `updatedAt` می‌آید،
و آهنگ‌های داغ `priority` بالاتری می‌گیرند.

#### رشد sitemap

الان حدود ۵۰ آدرس داریم. محدودیت هر فایل sitemap **۵۰٬۰۰۰ آدرس** است.
`MAX_TRACKS` فعلاً روی ۵۰۰۰ تنظیم شده. وقتی تعداد آهنگ‌ها به این عدد
نزدیک شد، باید به `generateSitemaps` مهاجرت کرد تا چند فایل تولید شود.
در Next 16 پارامتر `id` یک Promise است:

```ts
export async function generateSitemaps() {
  return [{ id: 0 }, { id: 1 }];
}

export default async function sitemap({ id }: { id: Promise<string> }) {
  const page = Number(await id);
  // ...
}
```

## ۶. سرعت و Core Web Vitals

| اقدام | چه چیزی را بهتر می‌کند |
|---|---|
| رندر سمت سرور + ISR | TTFB و FCP |
| `next/font` با `display: swap` | LCP؛ فونت خودمیزبان است، درخواست خارجی ندارد |
| کاور با `aspect-square` و ابعاد ثابت | CLS — جای تصویر قبل از بارگذاری رزرو می‌شود |
| `priority` روی ۵ کارت اول | LCP |
| `sizes` دقیق روی هر تصویر | حجم دانلود |
| فرمت AVIF/WebP خودکار | حجم دانلود |
| `preload="none"` روی تگ audio | صفحه فایل صوتی را تا کلیک کاربر دانلود نمی‌کند |
| `Cache-Control: immutable` روی `/uploads/` و `/_next/static/` | بار سرور و بازدید دوم |
| `minimumCacheTTL` یک‌هفته‌ای برای تصاویر | CPU سرور |

فچ‌های مستقل با `Promise.all` موازی اجرا می‌شوند تا TTFB جمع نشود.

بعد از دیپلوی با <https://pagespeed.web.dev/> اندازه‌گیری کنید.

## ۷. دسترس‌پذیری (که روی SEO هم اثر دارد)

- هر صفحه دقیقاً **یک `<h1>`** دارد.
- سلسله‌مراتب `h1 → h2 → h3` رعایت شده.
- همه‌ی تصاویر `alt` معنادار دارند (کاورهای تزئینی `alt=""`).
- لینک «پرش به محتوای اصلی» برای صفحه‌کلید.
- `aria-label` روی دکمه‌های آیکونی پخش.
- `prefers-reduced-motion` رعایت شده.

## ۸. امنیت (سیگنال اعتماد)

در `next.config.ts`:

- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `X-Frame-Options: SAMEORIGIN`
- `Permissions-Policy` — دوربین، میکروفن و موقعیت مکانی بسته
- `poweredByHeader: false` — نسخه‌ی Next لو نمی‌رود

## ۹. کارهای بعد از دیپلوی (چک‌لیست)

این‌ها را **من نمی‌توانم انجام دهم** چون به حساب گوگل شما نیاز دارند:

- [ ] **Google Search Console**: دامنه را اضافه کنید،
      کد تأیید را در `NEXT_PUBLIC_GOOGLE_SITE_VERIFICATION` بگذارید و
      دوباره build/deploy کنید.
- [ ] **ثبت sitemap**: در سرچ کنسول `https://flmusic.ir/sitemap.xml` را ثبت کنید.
- [ ] **اجبار HTTPS در پنل پارس‌پک**: الان `http://flmusic.ir` هم جواب می‌دهد.
      تا وقتی هر دو باز باشند، گوگل ممکن است نسخه‌ی http را ایندکس کند.
- [ ] **Bing Webmaster Tools**: ثبت کنید (منبع ارجاع Copilot هم هست).
- [ ] **تست Rich Results** روی یک صفحه‌ی آهنگ و یک پروفایل.
- [ ] **PageSpeed Insights** روی صفحه‌ی اصلی و یک صفحه‌ی آهنگ.

### دو نکته‌ی محتوایی که رتبه را واقعاً تعیین می‌کنند

۱. **فیلد `genre` الان نام خواننده در آن ذخیره شده** («معین»، «هایده»،
   «داریوش») نه سبک موسیقی. صفحات `/genre/*` بر همین اساس ساخته می‌شوند و
   عنوانشان «آهنگ‌های سبک معین» می‌شود که هم برای کاربر گیج‌کننده است هم
   برای گوگل. پیشنهاد: یا ستون `artistName` جدا شود، یا `genre` واقعاً
   سبک بگیرد و نام خواننده جای دیگری برود.

۲. **اکثر آهنگ‌ها `description` و `coverUrl` ندارند.** توضیحات خالی یعنی
   متای تولیدشده‌ی کوتاه و صفحه‌ی کم‌محتوا («thin content») که گوگل به آن
   رتبه‌ی خوبی نمی‌دهد. پرکردن توضیح و کاور بیشترین اثر را روی رتبه دارد.
