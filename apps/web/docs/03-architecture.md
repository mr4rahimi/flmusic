# معماری و تصمیم‌های فنی

## جایگاه در monorepo

```
apps/
├── api/      NestJS — منبع همه‌ی داده‌ها
├── mobile/   Flutter — کلاینت موبایل
└── web/      Next.js — این پروژه
```

`apps/web` یک پکیج **مستقل** با `node_modules` و lockfile خودش است.
دلیل: در ریشه‌ی مخزن `pnpm-workspace.yaml` وجود ندارد و `apps/api` هم
همین‌طور مستقل است. اضافه‌کردن workspace یعنی نصب دوباره‌ی همه‌چیز و
ریسک شکستن بیلد API — که ارزشش را نداشت.

## جریان داده

```
مرورگر → Next.js (سرور) → NestJS API → PostgreSQL / Meilisearch
                ↓
         HTML کامل + JSON-LD
```

هیچ درخواستی از **مرورگر** به API نمی‌رود. همه‌ی فچ‌ها در Server Component
انجام می‌شوند. نتیجه:

- توکن یا کلیدی در مرورگر قرار نمی‌گیرد.
- خزنده‌ی گوگل HTML آماده می‌بیند.
- روی سرور، فچ از `127.0.0.1:3000` انجام می‌شود و از CDN عبور نمی‌کند.

تنها استثنا فایل صوتی و تصاویر است که مرورگر مستقیم از `/uploads/` می‌گیرد.

## لایه‌بندی

### `src/lib/` — منطق خالص، بدون UI

| فایل | مسئولیت |
|---|---|
| `env.ts` | خواندن و نرمال‌سازی متغیرهای محیطی. تنها جایی که `process.env` خوانده می‌شود. |
| `types.ts` | شکل داده‌های API |
| `api.ts` | فچ، کش، مدیریت خطا، یکدست‌سازی شکل پاسخ‌ها |
| `seo.ts` | ساخت URL، slug، متن متا. **تنها منبع حقیقت مسیرها** |
| `jsonld.ts` | سازنده‌های Schema.org |
| `og.tsx` | کارت تصویر اشتراک‌گذاری |
| `format.ts` | قالب‌بندی فارسی: مدت، تعداد، تاریخ، ارقام |

> همه‌ی لینک‌های داخلی از `routes` در `seo.ts` ساخته می‌شوند.
> اگر ساختار URL عوض شود، فقط همان یک فایل تغییر می‌کند و
> sitemap، canonical و JSON-LD خودبه‌خود همگام می‌مانند.

### `src/components/` — کامپوننت‌های مشترک

پیش‌فرض همه **Server Component** است. فقط سه فایل `'use client'` دارند:

- `player/PlayerProvider.tsx` — تگ `<audio>` و state پخش
- `player/PlayButton.tsx` — دکمه‌ی پخش
- `player/PlayerBar.tsx` — نوار پایین صفحه
- `SearchBox.tsx` — ورودی کنترل‌شده

این «جزیره‌های کلاینتی» روی محتوای سرور-رندر می‌نشینند؛ حجم جاوااسکریپت
ارسالی کم می‌ماند و محتوا همچنان در HTML اولیه هست.

### `src/app/` — مسیرها

هر مسیر: `page.tsx` (رندر) + `generateMetadata` (متادیتا) و در صورت لزوم
`opengraph-image.tsx`.

## تصمیم‌های قابل‌بحث

### چرا کش با ISR و نه SSR خالص؟

آهنگ‌ها بعد از انتشار تقریباً تغییر نمی‌کنند. ISR یعنی صفحه یک‌بار ساخته
و تا انقضا از حافظه سرو می‌شود — TTFB در حد میلی‌ثانیه و بار روی API نزدیک صفر.
عدد revalidate هر صفحه با نرخ تغییرش تنظیم شده (جدیدترین‌ها ۲ دقیقه،
سبک‌ها ۱ ساعت).

### چرا پخش‌کننده در layout ریشه است؟

اگر داخل صفحه‌ی آهنگ می‌بود، با هر ناوبری unmount می‌شد و پخش قطع می‌شد.
در layout ریشه، ناوبری App Router آن را زنده نگه می‌دارد.

### چرا `apiGetSafe` وجود دارد؟

بخش‌های جانبی صفحه (مثل «آهنگ‌های دیگر این هنرمند») نباید با قطعی موقت
API کل صفحه را ۵۰۰ کنند — یک صفحه‌ی ۵۰۰ برای گوگل بدتر از یک صفحه‌ی
ناقص است. در مقابل، صفحه‌ی آهنگی که وجود ندارد باید **۴۰۴ واقعی** بدهد،
نه صفحه‌ی خالی با کد ۲۰۰. `getTrack` و `getProfile` عمداً `null`
برمی‌گردانند تا `notFound()` صدا زده شود.

### چرا فیلتر `visibility/status` فقط روی بعضی endpointها؟

`/feed/*` و `/search` سمت سرور فیلتر شده‌اند و اصلاً فیلد
`visibility`/`status` را برنمی‌گردانند. اگر آنجا فیلتر می‌کردیم،
همه‌چیز حذف می‌شد. `/tracks/user/:username` موجودیت کامل می‌دهد و
آنجا فیلتر لازم است. توضیح کامل در [05-api-integration.md](05-api-integration.md).

### چرا `output: 'standalone'`؟

خروجی standalone فقط فایل‌های لازم برای اجرا را جمع می‌کند
(حدود چند ده مگابایت به‌جای صدها مگابایت `node_modules`).
دیپلوی سریع‌تر و مصرف دیسک سرور کمتر است.

## نکات Next.js 16

این نسخه تغییرات breaking دارد:

- `params` و `searchParams` **Promise** هستند و باید `await` شوند.
- در `generateSitemaps`، پارامتر `id` هم Promise است.
- `images.qualities` پیش‌فرض فقط `[75]` است.
- `images.minimumCacheTTL` پیش‌فرض از ۶۰ ثانیه به ۴ ساعت رفته.
- بهینه‌سازی تصویر برای IPهای محلی به‌طور پیش‌فرض بسته است
  (`dangerouslyAllowLocalIP`). چون میزبان رسانه‌ی ما عمومی است مشکلی نیست.

مستندات نسخه‌ی نصب‌شده داخل خود پکیج است:
`apps/web/node_modules/next/dist/docs/`
